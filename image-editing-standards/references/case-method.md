# 修改前与最终确认的对比方法

用户要求用修改前和最终确认图总结问题及解决方案时，必须先确认“最终”身份，不能只选文件名最高的版本。

## 确认标签

- **U：用户最终确认**。用户明确认可该图/该版本的整体结果，且没有在相同范围继续指出问题。保存原话和版本关联。后续推翻则更新状态。
- **P：局部认可**。例如“都好着就是冰雹不真实”只认可其他部分，冰雹仍未通过；不是整张确认。
- **V：视觉自检**。助手看过并认为合格，尚无用户确认。
- **T：技术证据**。尺寸、哈希、区外差异等核验存在，但视觉或用户确认不足。
- **R：仍在返工/被否定**。用户指出本版错误，不能再当正确范本。
- **X：证据缺失**。没有可读取原图/最终图、缺版本关系、只有交付宣称。保留记录，不能伪造对比图。

标签可并列，如P/T；不要用一个“成功”合并不同证据。执行许可“对开始”不记U；对“要删异常细线吗”回复“嗯”是许可，不能证明还没做出的成稿通过。

## 版本与图像对齐

1. 找用户原话、助手实际交付路径和相邻轮次，建立 before → candidate → user feedback → revision 的链。
2. 检查文件是否存在、可读取；记录SHA-256、宽高和拍摄/生成来源。最新任务还在运行时，只做带时间的快照，不修改其文件，不把当前候选冻结成最终认可。
3. 标注对比基准：最早原图、当前修复母版和失败候选不是同一概念。只修两边时可对照本轮母版，但要另检查相对于已确认整图是否退步。
4. 相同画布以同坐标裁切；尺寸不同只为展示可做等比缩略，图注注明尺寸和裁切，不据此宣称像素相同。
5. 对比包括整图、问题局部和必要实物参考。对照中不能用强锐化、调色或不同倍率偏袒某版本。
6. U不足时显示“未找到用户最终确认”，可对最近修订方案做方法分析，但不称已解决或最终标准。

## 归纳方式

每个案例写清：现象 → 用户影响 → 有证据的处理/尚待验证方案 → 验收项 → 不可重犯的规则。

视觉现象可直接观察；根因若只有推测就写“可能原因”。脚本记录“统一透视”是过程证据，不自动证明透视正确；需要实图检查与用户反馈共同判断。

## 可移植性与隐私

Skill保留必要的匿名化案例、任务ID和缩略对照，不复制完整私人聊天。完整索引留在本机审计目录，不随公开包发布。用户没有授权GitHub同步时不上传；需要同步时先检查是否含本机绝对路径、人物图片、聊天原话等不适合公开的内容并按当前授权处理。
