# 网站 UI 走查 → 飞书多维表格

**这是总体「网站走查」主 skill**（本仓库目录：`ui-visual-audit-feishu`；调用名 `UI走查-飞书` / `$ui-visual-audit-feishu`），**不是**某个品牌站专用 skill。  
品牌/项目专册可另建或放同目录专项文件；**通用规范只沉淀进本 skill**。与团队 `ui-acceptance-assistant` 同源同步。

提效助手，不替人拍板。证据门槛、最小单元拆解、高风险双证据；合并标注图、按容器节点量间距、视口敏感性、多语言去重、协作表保护。细节与命令见 [reference.md](reference.md)，脚本见 `scripts/`。

## 0. 开工前（缺一项就先问）

- 线上 URL（各语言版本）、Figma 文件 key + 各页 PC/移动 node-id（用 REST 读，token 只在本机环境变量里用，**不回显、不写进文件**，结束时提醒用户撤销）
- 范围：哪些页面/端/语言；是否含交互（默认只做静态默认态）
- 飞书：目标 Base/表 URL。先 `lark-cli auth status`，再 `+field-list`、`+view-list` 读结构；**用户的表优先，字段/选项照用户现有的，不自创**
- 基准视口：PC 1920、移动 390（Figma 只有这两档；其它宽度只用于判断“是否宽度相关”，不拿来逐像素比）

## 1. 取证（每个模块都要两份证据）

1. **Figma**：`scripts/figma_boxes.py` 读节点 → 文本（字号/字重/字距/行高/色值/可见性）、容器框（位置/尺寸/圆角）。务必检查**祖先链 visible**（设计稿常有隐藏的重复画板，会读到错位置/错颜色）
2. **线上**：`scripts/capture_live.js` 在基准宽度下取 DOM + 计算样式 + 整页截图（先滚动触发懒加载、等字体）。文案从 DOM 读，不靠截图看

### 截图硬规则（2026-11-23）
- **必须等配图加载完成再截**：整页滚动触发懒加载后，检查可见大图 `complete && naturalWidth>40`，达标率不够不准截；截完还要用像素抽检（产品卡图区不能大片纯白）。白底未出图的标注图禁止上传飞书。
- 标注图要让人一眼看懂问题：上设计稿、下线上，红框对准出问题的元素；同类问题多张卡写「几张同样/三张同样」，不要每张各占一行却图还是空的。

3. **对齐成同尺度图**：同一缩放比例裁出设计/线上同一区域（`scripts/annotate.py`）
4. 只有 DOM/CSS 无法证明、但目视有差异时才做像素差分；差分只是辅助，必须映射回具体元素

**最小单元**：容器、边框、圆角、底色、阴影、图标（逐个）、文字层、间距、位置，逐个核；不能只看父容器。
**高风险四类要双证据**：背景色（元素计算色 + 同区域截图）、图标（Figma 节点/资源 + 线上 SVG 尺寸与描边）、文字样式（Figma 参数 + 线上计算样式）、hover（默认态+hover 态）。两份证据对不上就不写，先查视口/选择器/状态。

### 量法硬规则（上次被用户纠正过）
- **间距量“容器”，不量“内容”**：卡片/按钮/格子之间的间距=相邻**容器框**边到边；不要量 Logo/图标之间的距离（内容大小不同，间距必然不同）。设计稿内部本来就统一，如果量出“设计稿自己不一致”，先怀疑量错对象
- 标注图上写数值并框出被量的空隙，设计稿与线上用同一倍率
- **颜色深浅**：同时报“节点标注色值”和“渲染后墨色浓度”（同区域像素统计）。标注色值相同但渲染观感不同时，如实写“观感偏深/偏浅（色值同为 #xxxxxx）”，并附字距/字号差异，不要硬写成色值不一致；用户坚持时以用户看到的为准并请其指认节点
- 数值只写有来源的（Figma 参数/DOM/像素统计）；没有就写“视觉偏大/偏小”并勾“需人工复核”

## 2. 哪些写、哪些不写

- 只写**差异**，不写“一致/正常”。每条指明元素、现状、设计期望
- **删掉很小的问题**：位置/对齐差几个像素且肉眼不影响、标题与副标题位置略不齐这类。用户提过同类就整类去掉，并主动排查同类一并去掉
- **视口规则**：仅因切换设备导致的重排/换行不记。但在 1920/390 基准下就能看到的差异要记，并在备注标“宽度相关”
- **多语言去重**：同一问题在英文页和德文页都有时，只记英文页；德语只记**德语特有**的（译文不准、漏译、连字符/拼写、长词溢出或折行、称呼 Sie/du 不统一、多出/缺少内容）。德语条目的“备注说明”写【优化建议】+【建议译文】（具体到德语单词，不确定的标需人工复核，并提醒母语者复核）
- CMS/动态内容（新闻、日期、顺序）默认不算 UI 问题，除非用户要求验内容
- 用户已删除的问题不重复加；复核后确认仍存在，只提示并询问是否恢复
- 设计稿自身的错别字/疑似问题，单独提示，不当成线上缺陷

## 3. 标注图（核心交付物）

**同一模块、同一端的问题合并到一张图**：上设计稿、下线上，同倍率，红框 + 红色圆形编号，图下带图例（一行一条，与表里的描述对应）。一二三四轮附图要求相同（2026-11-26）。
- **左上角标明「设计稿」「线上」**；禁止多余符号/装饰
- 每个编号只框它对应的那个元素；框不准就整张重做，不要乱画
- 多个同类元素（如 5 个圆形图标）只在第一个框上放编号，其余只画框
- 间距类问题框的是“空隙”
- 表里该组每条记录都附这张图，“备注说明”写【对应图中标注 n】（只有一条问题的模块不需要）
- 图中不放无关红框；检查标注是否落在正确位置再写入（缩略图拼图 QA，必要时看原图；读图工具会缓存同名文件，复查时换新文件名）

## 4. 问题描述写法（对齐用户自己的写法）

短、直接、像对前端说话：`【模块】元素 + 现状 → 设计稿`，一句话讲完，不写过程/道歉/背景。
- 好：`【Quality】步骤圆形图标底色不一致：设计稿 #F5B301，线上 #F4C400`
- 好（用户风格）：`背景切图图层选错了，少了黑色遮罩层`、`图标小了，看看是不是导出图层时没选对`
- 不好：整页不一致、很多地方有差异、带“经检查发现”“建议考虑”
- 用户**已手改**的描述视为权威，不覆盖；新发现的相关问题另起一行
- **用户已补充过的问题禁止再补一遍**（2026-11-26）：表里已有同模块同现象（含用户手写）→ 不重写问题描述、不新开重复行、不重复贴同义二轮/三轮说明；只核是否仍不通过，缺对准图才补图
- 能判断成因就带一句（切图选错图层 / 缺蒙版 / 素材未替换 / 未用高清图），前端好定位
- **文案差异**只圈出位置，写“文案和设计稿不一致”，不抄原文
- **折行差异**：不影响美观、不拥挤、模块高度和间距没变 → 不计；折行过分导致高度/间距增减、影响观感 → 必须计
- **配图清晰度（PC 和移动端都必查，逐张查，不要因为麻烦漏掉）**：线上配图大多是 1× 素材（自然宽≈显示宽），设计稿多为 2×–7×，高清屏上会偏糊。用 DOM 里 `naturalWidth ÷ 显示宽` 与设计稿图片原始像素 ÷ 显示宽对比，线上 ≲1.5 且设计稿明显更高的都要记；覆盖主图、缩略图、选项图、场景头图、技术特点卡、居家场景、尺寸图、套装小图、支架清单图、安装步骤图、配送横幅等所有位图。统一写法：`线上配图和设计稿相比同位置过于模糊，需替换高清图`，并附“上设计稿清晰 / 下线上发糊”的放大对比图（编号对应）
- 标题前黄色竖条要单独框出并说明偏粗/偏细、偏长/偏短；头图要查“与页签栏的间距、图片露出范围、遮罩”；框不能贴在图片边缘看不见，也不能被编号标签压住

## 5. 写入飞书（一张表装所有页面）

结构（以用户现有表为准）：`页面`（Branding / About us / Support …，新页面加选项）→ `尺寸`（PC端 / 移动端，同级）→ 模块按页面顺序排列；`语言`（英文 / 德语 / 双语）；`所属模块` 用 `01 Header … 15 Footer、16 全局` 带序号的选项。视图按 `页面 → 尺寸` 分组，再按 `所属模块` 升序排；模块不再单独分组。
默认值：`前端是否完成优化` 不勾；`UI验收是否通过` 留空（复验后才填）；`需人工复核` 默认不勾，仅证据不足且复查后仍不确定时勾；优先级 P0–P3、问题类型从表里现有选项里选（定义见 reference.md）。

**协作表保护（最重要）**
- 表里有别人（设计/前端）在同时编辑。写之前先 `+record-list` 拉最新；写入/改动只动自己创建的记录
- **绝不静默删除或改写他人记录**。关键字段全空的空白行可直接删（2026-11-26 用户确认）；有残留内容的不要当空白删。删除前尽量用 `+record-history-list` 看谁改过
- 用户改了的字段（页面、模块、语言等）以用户为准，不改回去
- 只改视图配置/排序这类“排版”需求时，不碰任何记录，改完核对条数不变
- 重排序号时先确认该字段还存在（用户可能已删“区块顺序”，则靠视图排序）
- 回答“是不是丢数据”这类问题，用事实：记录历史、条数、逐条对照清单，不凭印象

写入流程：`scripts/feishu_write.py` 先 `--dry-run`，再批量建记录（≤200/批）→ 逐条上传附件（相对路径）→ 回读校验（条数、每条仅 1 张附件、无空白行、模块序号单调、尺寸/页面正确）。每个里程碑弹 macOS 通知；任务卡住就自己停下并说明阻塞点。

## 6. 汇报（中文，简短）

结论 + 数量 + 去掉了什么 + 限制，例如：Figma 只有 1920/390 两档、德语译文未经母语者复核、导航下拉/hover 未覆盖、颜色类按渲染观感量。不在聊天里贴 DOM/坐标/整张图；证据都在飞书附件里。
明确说出“是否执行了逐元素像素级流程”和“哪些步骤被阻塞”。

## 经验教训（网站走查通用沉淀，每次走查必过）

> 纠正必须写回**本 skill**（通用）。  
> 禁止把通用规范写成某品牌站专用 skill 命名；项目特例只进项目专册或个人 playbook 附录。

用户肉眼能一眼看出来、但最容易漏的七类，每个模块、每个端（PC/移动）、每种语言都要单独扫一遍：
1. **选中态**：卡片/缩略图/页签选中后的描边、光晕、勾选图标大小。注意“边框 + box-shadow 外圈”叠成两条线（线上 `border 2px` + `box-shadow 0 0 0 2px 淡黄`，设计稿只有一条）。
2. **双层描边**：同时看 border、box-shadow、outline、inset shadow；颜色相同的 inset 只是加粗，不算双线。
3. **德语/英语文案**：Figma 全部可见文字与线上逐字比对（含标点、空格、€ 位置、“Menge/Anzahl”、按钮后缀“legen”）。英文页再做“与德文页同字串=未翻译”扫描。
4. **箭头/小图标**：切换箭头、数量器 −／＋、勾选图标的 **图标本身尺寸与粗细**（按钮外框一样大不代表图标一样大），放大看。
5. **圆角**：主图、缩略图、卡片、提示框、按钮逐个量。
6. **间距**：量标题→卡片、卡片→卡片、区块→区块；PC 与移动分别量。
7. **字号/字重/颜色/下划线**：移动端常整体比设计稿小约 2px（14→16、12→14）；免责小字多为 10–13px #888，设计稿 14px #666。

方法：`scripts/_textcap.js`（线上全部文字+带边框/阴影/底色的容器，含三个页签态与整页截图）→ `figflat.py`（Figma 可见文字/容器，跳过隐藏层）→ `textcmp2.py`（按文字匹配，输出字号/字重/颜色/下划线差异和文案差异，匹配多个时取与整体偏移最接近的那个）→ `ann.py`（按文字定位自动画编号红框）→ `fs.py`（更新描述/加附件/新建）。再用同宽并排裁图肉眼复核一次，因为 DOM 值相同但视觉不同的情况存在（如图片盖住灰底）。

写法：同一问题涉及多张图，只写一句“……每张都需要还原设计稿，现在缺少……”，配 2–3 张代表图；字号/颜色/字体写“线上值 / 设计稿值”；标注n 与红框编号一一对应；新增标注接着旧编号，新图放第二/三张附件，描述里写“见第二张图”；先查现有记录避免重复；不写任何 AI/工具口吻。
注意：截图里异步加载的支付按钮可能没渲染出来，涉及它时用早先正常的整页图。

### 营销/首页类页面（通用）
首页/营销页走查时，**圆角、卡片轮播是否撑满整页、轮播指示点、版心、主标题折行/位置**常是大问题，必须主动量、主动记；不能因为「某站 PDP 版心不算」就整站跳过。移动端与 PC 同等严查。用户已圈的通栏/撑满问题优先于细项；同类「未撑满」在不同模块是两条，不能互相顶替。

### 二轮/说明纠错（通用 · 2026-11-26）
- 说明必须准确清晰：`端 + 模块 + 元素 + 怎么不对`；禁止「原问题仍在」空话。
- 附图必须对应模块：禁止用别的模块图顶替；用户手补行必须用用户原标注图。
- 原先写错的：重写说明/换对准图；确属错行才删；关键字段全空的空白行可直接删。
- 边界不清先问用户；项目特例查项目专册，不要猜。

### 营销合作/含肖像素材页（通用）
- **未确认肖像权素材一律不走查、不写入**。
- **已确认 Banner 必须严查**：字体、品牌条与标题位置、主视觉与标识模糊。
- **只记本页模块**，全站 Header/页脚不要硬塞进该页面（除非用户要求）。
- **达标循环**：还能挑出明显漏项就继续查到勾完清单为止。

### 磁盘卫生（所有走查通用）
- **不要往用户桌面写走查工作区**；用本机缓存目录（如 `~/Library/Caches/*-walkthrough/`），交表后删大图缓存。
- 主动清理桌面上助手留下的旧 `*走查*` / 复核垃圾目录；保留用户自己的设计物料。

### 标注图质量与去重（2026-11-24）
- 图上中文禁止方框乱码：必须用 Arial Unicode / 冬青黑等，失败就中止，禁止 `load_default`。上传前用读图工具确认「Figma 设计稿 / 线上实现 / 图例」汉字可读。
- 同模块相邻行禁止同义重复（尤其「过于模糊」写两遍）；模糊专行存在时，类型/位置行不要再写模糊。每页扫一遍相邻行。
- 配图本身要清晰（够 DPR、PNG、LANCZOS），上传前目视检查，禁止马赛克级缩略图。
- 精细清单（双端双语逐步勾）：图标、颜色、背景、投影、描边、卡片/模块间距、蒙版、渐变、清晰度、双语文案、影响观感的折行、圆角、卡片/模块高度、轮播按钮与箭头大小。

### 标注红框必须框到问题上（2026-11-25 用户强调）
- **红框只能框问题元素本身**（如图标本体），禁止框整张卡/整行/空白/相邻文字却声称在标图标。
- 设计稿与线上的红框必须框**同一类同一位置**的元素；对不准就重裁/重量 DOM，不准交「框飘了」的图。
- 同类多个（如 7 个步骤图标）：第一个放编号，其余只画框，框仍要落在每个图标上。
- **上传前必须用读图工具目视验收**：框是否落在问题上、图是否清晰可读；不达标整张重做，禁止凑合上传。
- 用户每次纠正（框不准、图糊、描述啰嗦、漏图标等）必须立刻写回本 skill「经验教训」+ 个人记忆，下次开工先读。

### 走查配图清晰度硬规则（2026-11-25 用户强调）
- 抓线上截图默认 `device_scale_factor≥2`；标注用图禁止把糊图再缩小当证据。
- 图标对比图要**放大到能看清线形粗细**（单独 zoom 条），不能只靠整页缩略图「感觉不一样」。
- 图糊就看不出问题 → 先重抓清晰图再对比；清晰度不够不准下「无差异/已通过」结论。

### 实事求是 / 95% 还原（2026-11-25 用户再纠正）
- **约95%还原即可通过**，不要没事找事、不要把接近设计稿的细节硬写成不通过。
- **禁止错模块对比**：设计稿与线上必须是同一区块（如底部CTA对底部CTA）；卖点图标条和CTA横幅拼一张 = 胡编，整张作废。
- 用户指出「看不懂你在说什么 / 我看着没问题」时：先怀疑自己对错模块、图糊、描述含糊；优先改通过或重做证据。
- 线上素材本身发糊才记清晰度问题；助手自己交的糊对比图不算「线上问题」。
- **95% 不覆盖用户已圈定问题**（2026-11-25 再纠）：用户红框圈过的图标（如四指标图标）、以及配图模糊（Logo/产品图）必须继续记不通过，直到修好；禁止自行改通过或从表里删掉。

### 飞书行顺序（再次强调，首页/营销页同样适用）
视图分组是「页面 → 尺寸」，**组内顺序 = 创建顺序**。必须按页面从上到下的模块顺序建行；页面专项走查时从该页**内容模块**起排（本页不含全站 Header 则不要硬塞 Header）；禁止把补记行甩到整表末尾。同模块多行必须相邻；禁止一行混多个模块。写完用回读清单核对模块单调，不对就删自己的行按序重建。



### 用户反复强调的硬性格式规则（每次写表前先对一遍，不要再犯）
- **每个单元格（每条记录）最多 3 条“标注”**。超过 3 条必须拆成相邻的多条记录，每条各自从“标注1”重新编号，图上红框编号同步重编，描述和图一一对应。4 条、5 条、7 条挤一格会让人漏看，不允许。
- **同一模块的问题相邻放置，按页面从上到下的顺序**；新增问题插入对应模块的位置，不要追加到表尾。需要调整顺序时删除重建（视图按创建顺序展示）。
- **描述极简**：只写“XX和设计稿不一致，需还原设计稿”“偏远/偏近/偏高/偏低”；不堆数字、不写工具/AI 口吻；文案类写“应为……”。
- **图上要圈出问题处并标清“设计稿 / 线上”**；英文页没有设计稿对照时标“线上英文页”。
- **模块名放在描述最前面的【模块·子项】**（表里没有“所属模块”列时）；每个模块、每个端、每种语言都要核对，不能只盯第一个模块。
- 不改、不删用户手写的记录。

## 通用补充（全站适用）
- 设计稿气泡里的交互（如 hover 放大）要按用户要求验收。
- 无障碍「Skip to content」误显等全站 Header 问题：记到约定的全局/Header 归属，不要每个子页重复堆。
- Logo 回首页等全站链：各页核一遍即可；已正确不建行。

- **PC/移动严格分开**：PC问题只写PC、只配PC图；移动问题只写移动、只配移动图。禁止写「PC/移动同」。标注条只能在图上方/下方，禁止黑条压住内容。

- **轮次门槛**（2026-11-26）：前端未勾「是否完成优化」→ **禁止**做二轮/三轮/四轮验收；不写本轮说明、不贴本轮图。只有勾了优化才开始对应轮次走查。
- **页面范围**（2026-11-26）：用户点名哪一页、哪一轮，只动那一页那一轮；禁止猜、禁止顺手全表、禁止改其它页。不确定先问。
- **手补归模块**（2026-11-26）：每条先下载并展示用户原截图，再问归哪块；禁止只抛文字。一次只确认一道红框/一对模块，避免一张多框时说混。
- **清误写二轮**（2026-11-26）：只清本页二轮说明+二轮图；不动问题描述/问题截图。若视图筛「待验收/不通过」，清完把未优化行改回「待验收」，禁止留空导致页面分组消失。
- **二轮判定**：已修好才通过；未修好/证据不足=不通过。禁止用含糊「约95%」把未修问题改通过。新问题新开行；PC/移动分开。
- **复现/回退**（2026-11-26）：曾通过又不行 → 取消「前端是否完成优化」✅；问题写入**后一轮**字段（二轮过了写三轮，三轮过了写四轮）+ 对准图。

### 前端反馈：各轮说明与附图（通用）
- 不通过说明要让前端看懂：端 + 模块 + 元素 + 哪里不对。
- 附图必须对应同一问题；错模块图整张作废重做。禁止用通用糊图顶替。
- 自检：读说明能否定位问题；看图红框是否落在该元素上。
