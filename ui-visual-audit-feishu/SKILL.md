# UI 走查 → 飞书多维表格

提效助手，不替人拍板。取自 `ui-acceptance-assistant`（证据门槛、最小单元拆解、高风险双证据）并吸收实战教训：
合并标注图、按容器节点量间距、视口敏感性、多语言去重、协作表保护。细节与命令见 [reference.md](reference.md)，脚本见 `scripts/`。

## 0. 开工前（缺一项就先问）

- 线上 URL（各语言版本）、Figma 文件 key + 各页 PC/移动 node-id（用 REST 读，token 只在本机环境变量里用，**不回显、不写进文件**，结束时提醒用户撤销）
- 范围：哪些页面/端/语言；是否含交互（默认只做静态默认态）
- 飞书：目标 Base/表 URL。先 `lark-cli auth status`，再 `+field-list`、`+view-list` 读结构；**用户的表优先，字段/选项照用户现有的，不自创**
- 基准视口：PC 1920、移动 390（Figma 只有这两档；其它宽度只用于判断“是否宽度相关”，不拿来逐像素比）

## 1. 取证（每个模块都要两份证据）

1. **Figma**：`scripts/figma_boxes.py` 读节点 → 文本（字号/字重/字距/行高/色值/可见性）、容器框（位置/尺寸/圆角）。务必检查**祖先链 visible**（设计稿常有隐藏的重复画板，会读到错位置/错颜色）
2. **线上**：`scripts/capture_live.js` 在基准宽度下取 DOM + 计算样式 + 整页截图（先滚动触发懒加载、等字体）。文案从 DOM 读，不靠截图看
3. **对齐成同尺度图**：同一缩放比例裁出设计/线上同一区域（`scripts/annotate.py`）
4. 只有 DOM/CSS 无法证明、但目视有差异时才做像素差分；差分只是辅助，必须映射回具体元素

**最小单元**：容器、边框、圆角、底色、阴影、图标（逐个）、文字层、间距、位置，逐个核；不能只看父容器。
**高风险四类要双证据**：背景色（元素计算色 + 同区域截图）、图标（Figma 节点/资源 + 线上 SVG 尺寸与描边）、文字样式（Figma 参数 + 线上计算样式）、hover（默认态+hover 态）。两份证据对不上就不写，先查视口/选择器/状态。

### 量法硬规则（上次被用户纠正过）
- **间距量“容器”，不量“内容”**：卡片/按钮/格子之间的间距=相邻**容器框**边到边；不要量 Logo/图标之间的距离（内容大小不同，间距必然不同）。设计稿内部本来就统一，如果量出“设计稿自己不一致”，先怀疑量错对象
- 标注图上写数值并框出被量的空隙，设计稿与线上用同一倍率
- **颜色深浅**：同时报“节点标注色值”和“渲染后墨色浓度”（同区域像素统计）。标注色值相同但渲染观感不同时，如实写“观感偏深/偏浅（色值同为 #xxxxxx）”，并附字距/字号差异，不要硬写成色值不一致；用户坚持时以用户看到的为准并请其指认节点
- 数值只写有来源的（Figma 参数/DOM/像素统计）；没有就写“视觉偏大/偏小”并勾“需人工复核”

## 2. 哪些写、哪些不写

- 只写**差异**，不写“一致/正常”。每条指明元素、现状、设计期望
- **删掉很小的问题**：位置/对齐差几个像素且肉眼不影响、标题与副标题位置略不齐这类。用户提过同类就整类去掉，并主动排查同类一并去掉
- **视口规则**：仅因切换设备导致的重排/换行不记。但在 1920/390 基准下就能看到的差异要记，并在备注标“宽度相关”
- **多语言去重**：同一问题在英文页和德文页都有时，只记英文页；德语只记**德语特有**的（译文不准、漏译、连字符/拼写、长词溢出或折行、称呼 Sie/du 不统一、多出/缺少内容）。德语条目的“备注说明”写【优化建议】+【建议译文】（具体到德语单词，不确定的标需人工复核，并提醒母语者复核）
- CMS/动态内容（新闻、日期、顺序）默认不算 UI 问题，除非用户要求验内容
- 用户已删除的问题不重复加；复核后确认仍存在，只提示并询问是否恢复
- 设计稿自身的错别字/疑似问题，单独提示，不当成线上缺陷

## 3. 标注图（核心交付物）

**同一模块、同一端的问题合并到一张图**：上设计稿、下线上，同倍率，红框 + 红色圆形编号，图下带图例（一行一条，与表里的描述对应）。
- 每个编号只框它对应的那个元素；框不准就改成纯并排对比，不要乱画
- 多个同类元素（如 5 个圆形图标）只在第一个框上放编号，其余只画框
- 间距类问题框的是“空隙”，旁边写 px
- 表里该组每条记录都附这张图，“备注说明”写【对应图中标注 n】（只有一条问题的模块不需要）
- 图中不放无关红框；检查标注是否落在正确位置再写入（缩略图拼图 QA，必要时看原图；读图工具会缓存同名文件，复查时换新文件名）

## 4. 问题描述写法（对齐用户自己的写法）

短、直接、像对前端说话：`【模块】元素 + 现状 → 设计稿`，一句话讲完，不写过程/道歉/背景。
- 好：`【Quality】步骤圆形图标底色不一致：设计稿 #F5B301，线上 #F4C400`
- 好（用户风格）：`背景切图图层选错了，少了黑色遮罩层`、`图标小了，看看是不是导出图层时没选对`
- 不好：整页不一致、很多地方有差异、带“经检查发现”“建议考虑”
- 用户**已手改**的描述视为权威，不覆盖；新发现的相关问题另起一行
- 能判断成因就带一句（切图选错图层 / 缺蒙版 / 素材未替换 / 未用高清图），前端好定位

## 5. 写入飞书（一张表装所有页面）

结构（以用户现有表为准）：`页面`（Branding / About us / Support …，新页面加选项）→ `尺寸`（PC端 / 移动端，同级）→ 模块按页面顺序排列；`语言`（英文 / 德语 / 双语）；`所属模块` 用 `01 Header … 15 Footer、16 全局` 带序号的选项。视图按 `页面 → 尺寸` 分组，再按 `所属模块` 升序排；模块不再单独分组。
默认值：`前端是否完成优化` 不勾；`UI验收是否通过` 留空（复验后才填）；`需人工复核` 默认不勾，仅证据不足且复查后仍不确定时勾；优先级 P0–P3、问题类型从表里现有选项里选（定义见 reference.md）。

**协作表保护（最重要）**
- 表里有别人（设计/前端）在同时编辑。写之前先 `+record-list` 拉最新；写入/改动只动自己创建的记录
- **绝不静默删除或改写他人记录**。空白行可能是用户“清空=想删”的习惯，也可能是正在编辑；先报告，得到确认再删。删除前用 `+record-history-list` 看谁改过
- 用户改了的字段（页面、模块、语言等）以用户为准，不改回去
- 只改视图配置/排序这类“排版”需求时，不碰任何记录，改完核对条数不变
- 重排序号时先确认该字段还存在（用户可能已删“区块顺序”，则靠视图排序）
- 回答“是不是丢数据”这类问题，用事实：记录历史、条数、逐条对照清单，不凭印象

写入流程：`scripts/feishu_write.py` 先 `--dry-run`，再批量建记录（≤200/批）→ 逐条上传附件（相对路径）→ 回读校验（条数、每条仅 1 张附件、无空白行、模块序号单调、尺寸/页面正确）。每个里程碑弹 macOS 通知；任务卡住就自己停下并说明阻塞点。

## 6. 汇报（中文，简短）

结论 + 数量 + 去掉了什么 + 限制，例如：Figma 只有 1920/390 两档、德语译文未经母语者复核、导航下拉/hover 未覆盖、颜色类按渲染观感量。不在聊天里贴 DOM/坐标/整张图；证据都在飞书附件里。
明确说出“是否执行了逐元素像素级流程”和“哪些步骤被阻塞”。

## 脚本（`scripts/`，已自测）

| 脚本 | 作用 |
|---|---|
| `figma_boxes.py nodes.json --y a b [--name 卡片] [--text 正则]` | 读 Figma 节点：文字参数/色值、容器框，自动跳过隐藏祖先 |
| `capture_live.js <url> <宽> <outDir> [高]` | 需 `npm i puppeteer-core`；整页截图 + 元素 rect/计算样式/祖先 opacity |
| `annotate.py`（`module_image(...)`，`--selftest`） | 设计/线上同倍率合并标注图，红框+编号+图例 |
| `feishu_write.py create/verify/blanks` | 批量建记录+传附件（`--dry-run` 先预演）、回读校验、只列空白行不删 |

## 检查清单（交付前逐项过）

- [ ] 范围/视口/语言已确认；Figma 读的是可见节点
- [ ] 每条有两份证据，高风险项有双证据
- [ ] 间距量的是容器；颜色同时给了色值和渲染观感
- [ ] 小问题已清；英德重复已去；视口相关项已标注
- [ ] 同模块同端合并成一张编号图，编号与描述对得上
- [ ] 描述短而直接；用户手改的没被覆盖
- [ ] 回读校验通过；他人记录未动；条数变化都能解释
- [ ] 提醒撤销 Figma token；列出未覆盖范围
